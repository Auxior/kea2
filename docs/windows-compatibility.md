# Windows 启动与子进程兼容修复

日期：2026-10-21；整合发布版本：0.1.5。基于用户提供、已在 Windows 本地验证可运行的 0.1.4 客户端进行对比和集成，未调整依赖版本或测试业务规则。

## 问题原因与修复

| 问题 | 原有行为与影响 | 整合方案 |
|---|---|---|
| Windows 虚拟环境进程转发 | 启动器要求 `subprocess.Popen.pid` 等于服务写入的 `os.getpid()`。虚拟环境的 `python.exe` 可通过中间进程运行解释器，导致服务已正常响应却无法通过就绪检查。30 秒后启动器进入退出清理，正在准备的测试收到停止信号，日志出现 `KeyboardInterrupt` | 启动器为每次启动生成随机 `launchId`，通过内部参数传给服务并写入就绪记录。匹配本次标识、工作目录和合法端口后，继续检查 HTTP 服务身份。PID 保留为诊断信息 |
| 非交互子进程继承控制管道 | 服务标准输入用于监听启动器停止命令及父进程消失。测试、ADB 查询和报告命令继承这一输入后，读取输入可能等待未关闭的控制管道，造成准备或报告流程阻塞。只修改就绪检查不能覆盖这一问题 | 对这三类非交互子进程显式设置 `stdin=subprocess.DEVNULL`，使其获得独立的空输入。启动器与服务之间继续使用原控制管道 |

`KeyboardInterrupt` 表示执行进程收到中断，不能单独证明用户点了停止、手机连接失败或 App 崩溃。排查时应结合启动器日志、运行时间以及 `run.json` 的最终状态和 `recentLogs`；部分报告生成异常只记录在 `recentLogs`，不一定出现在 `console.log`。

## 集成范围与兼容边界

- `launch_workbench.py` 与 `kea_workbench/__main__.py` 配套支持内部 `--launch-id` 参数。手动启动不需要该参数；重复双击仍可读取不含 `launchId` 的旧记录，再通过工作目录及 HTTP 身份检查复用已有服务。旧记录不能满足一次新启动的就绪检查。
- `kea_workbench/engine.py` 仅隔离测试和 ADB 查询子进程的标准输入；`kea_workbench/reports.py` 仅隔离原生报告命令的标准输入。
- 原有端口自动选择、启动锁、服务随启动器退出、Windows Ctrl+Break / POSIX SIGINT、停止等待上限、报告超时、测试参数及平台上报流程保持原逻辑。
- 修正测试中的 Windows 路径表示和 UTF-8 读取。未导入客户端的虚拟环境、构建缓存、设备数据、设置或历史报告。

## 回归验证

在本项目的 macOS / Python 3.14 环境执行 `.venv/bin/python -m pytest -q`，结果为 **53 项通过**。自动测试不连接真实设备或平台，覆盖以下行为：

- 服务就绪时 PID 不同仍可识别本次启动；旧启动标识、其他目录及不含标识的旧记录不能误判为本次就绪。
- 真实中间进程转发启动、端口冲突换端口、重复启动复用及立即重启。
- 启动器控制管道保持打开时，实际创建的设备查询、测试执行和原生报告替身子进程均可读到输入 EOF；正常结束和中途停止均保留进度、清理输出及报告。
- 启动器被结束或终端关闭时释放服务端口，以及既有参数校验、配置同步、上传并发、上报资格、业务回执和报告访问边界。

## 升级步骤

1. 先停止测试并关闭旧工作台。将包含本次修复的启动器和工作台源码配套更新到原目录，保留 `configs/`、`data/` 和 `artifacts/`。
2. 在包含 0.1.5 完整源码的目录中，使用原虚拟环境显式安装应用。只覆盖启动器不会更新已安装的模块；同版本手工补丁也可能被版本检查复用：

   ```powershell
   .\.venv\Scripts\python.exe -m pip install --index-url https://pypi.org/simple --force-reinstall --no-deps .
   .\start-windows.bat
   ```

3. 确认出现“Web 操作页面”提示后创建短时测试，核对步数增长、停止清理和原生报告。未完成或已取消的任务需要重新创建，不会自动续跑。

新 `launchId` 握手需要启动器和工作台模块同时更新；只替换其中一个文件不是完整修复。
