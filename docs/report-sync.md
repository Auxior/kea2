# 大报告同步与手动重试修复

日期：2026-10-21。

## 日志证据与原因

用户提供任务 `kea2-602e75fd74e843ed955436c41e4ade94`：

- 北京时间 2026-10-20 19:01:28 开始，2026-10-21 05:01:42 结束；本地状态为已完成，探索 36000.1 秒、32710 步。
- 请求与回执中的最后成功版本为 revision 557，但仍为 `phase: running`、`final: false`，没有确认最终结果。09:14 的记录仍显示上报失败。
- 原始报告约 164.88 MiB，含一个约 137.49 MiB 的 Fastbot 日志。包含工作台日志、参数及入口的上传快照共 14 个文件，约 172.85 MiB。
- 提示“本次过程报告上传超过 90 秒，下一周期继续同步”由本地文件循环的总时间预算抛出，不能据此认定存储服务器返回了 90 秒网络超时。现有日志没有逐文件耗时，无法进一步断言当时的网络带宽或哪个请求最慢。

原实现存在三个关联问题：

1. 时间预算耗尽后，最终上报线程直接退出，提示中的“下一周期”不会发生。
2. 上传确认只存在当前 `Publisher` 的内存中，手动重试创建新实例后从头上传。时间检查还发生在跳过未变文件之前，容易反复触及预算。
3. 手动重试没有先更新状态，页面既不禁用按钮也不展示受理反馈；若后台工作尚未结束，接口拒绝，而错误只显示在页面上部。没有服务访问日志，无法追溯每次用户点击的实际 HTTP 响应，但代码路径可以复现这两种无明显反馈的情况。

## 修复行为

- 成功上传一个文件后，将内容摘要和目标范围（存储端点、桶、前缀、运行编号）原子写入快照内的隐藏确认文件。失败文件不标记成功，目标变更不沿用其他目标的确认。
- 文件哈希与上传均使用流式读取，MinIO SDK 负责大文件分片。预算只在待上传文件之间生效，每轮至少允许一个待发送文件前进；不对已确认文件重新传输，也不上传内部确认文件。
- 续传复用不可变快照，避免活动日志增长导致后面的文件一直轮不到上传。执行完成后切换至最终快照，保留仍适用的文件确认。
- 上传完成后提交原有平台协议，并保留项目、外部运行编号、版本、统计与业务回执校验。响应不确定时对同一快照重复提交相同版本；最终成功后沿用同一平台任务，不创建重复运行。
- 预算耗尽或临时传输失败均安排下一轮，包括终态报告。一般 4xx（除 408/429）、回执校验失败或本地材料缺失等错误保留为可手动重试，不自动重复无效请求。关闭服务会停止等待中的重试；重启后中断的上报可手动恢复，已确认的最终成功状态继续保留。
- 手动请求返回 HTTP 202，立即清除旧错误并显示排队。上传中的重复请求返回当前进度；等待期间的重试唤醒原工作线程。
- 页面展示各阶段、文件和字节进度、当前文件、下次重试时间、最近成功时间，区分过程和最终同步，并增加 `delivery.log` 入口。

测试参数、上报资格、设备停止机制、HTTP 请求超时及业务回执校验保持原规则。修复不修改用户原始日志，也不代为向正式平台补报。

## 已有环境使用

关闭旧工作台，更新源码后使用原虚拟环境重新安装当前应用，再启动。保留 `artifacts/`、`configs/` 与 `data/`，不删除失败任务的本地材料。重新打开历史任务后点击“立即重试上报”，确认进度增长、平台确认和最终同步标记。若仍有网络错误，可从同一页面打开上报日志检查具体异常。
